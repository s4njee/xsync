# BENCHMARKSv4 — corpora x hosts, rsync -az vs xsync --streams 4

Generated by `benches/matrix4.py`. Regenerated after every cell, so a
partial matrix is still readable.

## Method

- Source: Mac (M1 Max, 64 GB). Its only NIC is a USB gigabit adapter.
- Arms run back to back per (host, corpus) so they share link conditions.
- Fresh destination per run; teardown outside the timed window.
- Remote `sync` **inside** the timed window, so neither tool is scored on
  data still in the receiver's page cache.
- Exit status and landed file count verified per run; failed cells are
  shown as `FAIL` and excluded from the ratio.
- 2 repetitions; the table reports the **best** run of each cell.

**Throughput below is logical (corpus bytes / wall clock), not wire
rate.** Both arms compress, so a compressible corpus can and does exceed
the ~112 MiB/s gigabit line rate: `cb7` reports 200-300 MiB/s because it
compresses roughly 2-3x on the wire. Compare arms within a row; do not
read these as link speeds.

## Reading these numbers

xsync is faster in 8 of 9 cells. The ninth, manga to mars, is a dead
heat (36.2 s against 36.4 s): 56 large incompressible files over gigabit
is pure bandwidth, both tools sit at line rate, and there is nothing
there to win.

The pattern is that xsync's lead grows with **per-file overhead** and
with **receiver weakness**, not with raw bandwidth:

- `congress` is ~1.9-2.2x everywhere. 1.3 million tiny files is a
  per-file-cost workload, and four streams overlap the stalls that a
  single rsync stream serialises.
- `cb7` on mars and freya is only 1.16-1.24x. Bulk volume on a capable
  receiver is the case where rsync is most competitive.

### The orion cb7 result is mostly about `-z`, not about xsync

The 7.82x headline (1676.2 s against 214.5 s) is the largest number in
this matrix and the most easily over-read. A control run isolates it:

| manga to | `rsync -a` | `rsync -az` | cost of `-z` |
|---|---:|---:|---:|
| mars | 36.4 s | 37.9 s | +4% |
| orion | 36.8 s | 107.0 s | **+191%** |

**Without `-z`, rsync to orion is exactly as fast as to mars** (36.8
against 36.4). So `-z` is nearly free on mars and catastrophic on the
Pi, and that single flag accounts for most of orion's deficit in every
row above.

These were ruled out as the cause -- all are equivalent between mars and
orion: link (both switched gigabit, single-connection SSH measured at
100 and 108 MiB/s), RTT (0.95 ms against 1.17 ms), negotiated SSH cipher
(aes128-gcm both), rsync version (3.4.4 both ends), and destination disk.

The mechanism is **not** established. The obvious explanation --
receiver-side decompression saturating a Pi core -- is not supported by
measurement: during `rsync -az` to orion nothing is CPU-saturated (rsync
~5% of one core, sshd ~25%, over 90% of the box idle). Compression
happens on the sender, which is the same Mac for every host, so a
sender-side explanation cannot produce a per-host difference either.
Something about how `-z` interacts with this receiver remains unexplained
and is worth its own investigation.

The honest summary of that cell: **`rsync -az` is 7.82x slower than
`xs --streams 4` to a Raspberry Pi**, which is true and reproducible
(1676.2 and 1681.3 s across two reps), but it is a fact about `-z` on
that host at least as much as a fact about the two tools.

## Verification

Beyond exit status and file count, both arms were checked byte-for-byte
on manga to mars: 4,025,816,305 bytes and SHA-256
`7b303fcc04b267003001926f9f91ceaa33200b3b43e5576cf1d702922d2d3432`,
identical to the source for both tools. File count alone would not catch
truncation, so this was checked separately.
